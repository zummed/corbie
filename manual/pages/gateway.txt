The gateway: an HTTP server that lets any program start Corbie runs and read their results.

Use it when the program that needs a run is not a Corbie client: a web
application, a script in another language, a webhook. That program sends HTTP
requests and needs no Corbie binary, config or keys.

How it works
------------

1. The gateway is a process that listens for HTTP requests. It is a Corbie
   client.
2. A program names a location and gives an input. The gateway starts a run
   there.
3. The program asks for the run by its ID, and gets its status and output as
   JSON.

Every request carries a token of the gateway's. A token names a client, and the
request acts as that client, limited by its ceiling, which no request can raise.

Start the gateway
-----------------

`gateway` is an argument of `corbie start`, alone or with `controller` and
`runner`. Set the computer up as in `corbie manual a-real-run`. `corbie up`
runs a gateway at a free port (`corbie manual a-project`).

  corbie start controller runner gateway --listen 127.0.0.1:8371
    gateway token (callers send it as Authorization: Bearer …): 179bd50585d04e741e0d5a254d7f6287cf5432cab12d7f31
    gateway for the client laptop-client, listening on http://127.0.0.1:8371

The gateway prints a new token each time it starts: `$TOKEN` below. With
`--token-file <file>` it reads a token from a file and prints none. A request
without a token of the gateway's gets 401.

Start a run
-----------

The gateway starts runs at locations of its client's trees. These are the
two files from `corbie manual first-machine`, submitted by that client.

  corbie run submit title.yaml
    /title   transient   recorded

The request is JSON with the location and the input.

  curl -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8371/runs \
       -H "Content-Type: application/json" \
       -d '{"at": "/title", "input": {"url": "https://example.com"}}'
    {"id":"laptop-client/20261013T185126.250Z-571d935912"}

Read the result
---------------

`$ID` is the `id` in that answer. `?wait` keeps the request open until the run
ends.

  curl -H "Authorization: Bearer $TOKEN" "http://127.0.0.1:8371/runs/$ID?wait"
    {"id":"laptop-client/20261013T185126.250Z-571d935912","machine":"fetch-title",
     "type":"flow","status":"done","input":{"url":"https://example.com"},
     "output":{"title":"Example Domain","url":"https://example.com"}, …}

Several clients
---------------

A gateway acts as one client for each `--client <config>`. Each config holds
one client, enrolled with its own ceiling (`corbie manual parties`).

1. A caller shows a token.
2. The token names a client, and the person the token was given to.
3. The gateway sends the request as that client.
4. The run's record names the person.

A line of the token file is a token, the client's name and the person.

  179bd50585d0   editor   alice@example.com
  93ab77c0e1f2   editor   bob@example.com
  5c11d2a09b3e   viewer

  corbie start gateway --client /etc/corbie/viewer --client /etc/corbie/editor --token-file tokens
    gateway for the clients viewer, editor, listening on http://127.0.0.1:8371

  corbie run show $ID
    editor/20261013T185126.250Z-571d935912  running  statechart door  step 1
      at: /door
      person: "alice@example.com"

- With no `--token-file`, the gateway prints a token for each client, and no
  request has a person.
- A list of runs names no person. `corbie run show <id> --record --json` gives
  the person of each event a client sent.
- Whoever has a token is its client. The gateway's computer holds each
  client's key.

Tokens of an OIDC issuer
------------------------

A gateway takes the tokens of an OIDC issuer, such as Microsoft Entra ID, so
that the issuer says who may be which client.

1. A caller gets a token from the issuer and shows it to the gateway.
2. The gateway checks the issuer's signature, the audience and the token's time.
3. The token's `roles` name the client: the first `--client` whose name is among them.
4. The token's `sub` is the person.

  corbie start gateway --client /etc/corbie/viewer --client /etc/corbie/editor --oidc-issuer https://login.example.com/tenant/v2.0 --oidc-audience api://corbie
    gateway takes the tokens of the OIDC issuer https://login.example.com/tenant/v2.0 for the audience api://corbie: the client is named by roles, and the person by sub
    gateway for the clients viewer, editor, listening on http://127.0.0.1:8371

  --oidc-issuer <address>   the issuer, as its tokens name it
  --oidc-audience <text>    who a token must be for
  --oidc-client <claim>     the claim that names the client; default roles
  --oidc-person <claim>     the claim that is the person; default sub

- For a person's sign-in name in Entra ID, give `--oidc-person preferred_username`.
- A token that is not taken gets 401, with the reason.
- The gateway has no page to sign in at. A caller gets its token from the
  issuer, and sends it as any token.

The command line through a gateway
----------------------------------

`corbie run …`, `corbie client secret …` and `corbie client value …` take
`--gateway <address>`. The command sends the token in `CORBIE_GATEWAY_TOKEN`,
and needs no config and no key on its computer.

  export CORBIE_GATEWAY_TOKEN=179bd50585d0
  corbie run submit house --gateway http://127.0.0.1:8371
    /house/devices/boiler   singleton   started editor/20261013T185126.250Z-571d935912
    /house/greet            transient   recorded

A command prints the same through a gateway as with the client's own config.
A Go program does the same with `client.Remote(address, token)`.

A run in another client's tree
------------------------------

The gateway's client starts a transient location of another client's tree as
a call. The location's file lists the gateway's client in `receive:`, and that
client's ceiling holds `send:` for the location.

  receive: [client:laptop-client]

The run is answered by its status, its output or error and the files the
output names, under the `id` the start gave. Its record is the other client's
and is not shown.

Other requests
--------------

  POST /trees                    submits a directory of machines
  POST /secrets, POST /values    sets, removes or lists secrets or values
  GET /runs                      lists runs
  GET /runs/<id>/record          the run's record; with ?watch, a stream of it
  GET /runs/<id>/files/<path>    a file of the run's result
  POST /runs/<id>/events         sends the run an event
  POST /runs/<id>/tickets        answers a ticket the run waits on
  POST /runs/<id>/cancel         cancels the run

The gateway keeps no state: each request reads or writes the store. Its
process must keep running, so it cannot run as a serverless function.
