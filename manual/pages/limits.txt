What Corbie does not defend against: Corbie makes no check and gives no protection in these cases.

A script uses files, the network, other programs, environment variables and
secrets only through permissions, and Corbie checks every use. It does not
defend against the following.

- A program that a job starts reads files, writes files and opens connections
  as the runner's user. Permissions are checked when it is started and not
  after. A runner's owner can run every started program in a sandbox or a
  container with `corbie start --exec-wrapper`, and Corbie provides none.
- A job allowed to read the runner's own files can read the runner's private
  key, and with it decrypt every job sent to that runner.
- A script allowed to connect to a secret's destination can learn the secret's
  value from that destination.
- A tool that a model's own program runs, switched on with `own:`, is not
  checked by Corbie. It can use everything its permission group allows, and
  Corbie records only that it was used.
- A plugin is trusted. One that opens a file, a connection or a program
  without asking Corbie is not checked, and only review of its code prevents
  that.
- Corbie knows whether a connection is encrypted when Corbie does the
  encryption. Where a service's own protocol does it, Corbie relies on what
  the plugin reports.
- Jobs on one runner are not isolated from each other. Send jobs that must be
  isolated to different runners, which a job selects with `tags:`.

These are true of definitions.

- An expression in an owner's definition runs in the controller's own process.
  Nothing limits its memory, and its one second stops its own code and not a
  call to something built in, so `'a'.repeat(2**40)` ends the controller and a
  regular expression that backtracks holds a step without end. An owner can do
  this to a controller that takes their definitions. Only a definition a client
  submitted runs in this process; one a job stored runs in a process of its own.
- An owner's expression is read and compiled in the controller's own process,
  and nothing stops that. Reading `=>` nested in what stands before another
  takes twice as long with each, and so does compiling a chain of `&&`, `||` or
  `??` whose left sides are fixed, so forty of either never finish. 4 MB of
  brackets ended a client for want of stack, and the controller reads an
  expression with the same code.
- Nothing limits what reading a definition costs the process that reads it. An
  owner's definition costs this to their own client and controller. A
  job's definition costs that job, and past its limits the job fails.

  400 KB of brackets in one expression          2 seconds, 1 GiB
  4 MiB of YAML that writes [1,1,...]           2.3 seconds, 660 MiB
  14 levels of files that name the next twice   3.9 seconds, 230 MiB

- Each step of a machine made while running, and each step after the first of
  an agent with a `list:` tool, is taken in a process of its own, and may use
  10 seconds and 1 GiB of memory. Past either, that machine fails and nothing
  else does. Machines that each use a step's whole time delay other
  runs, because the controller waits for four such steps at a time, and a run
  waits like that each time the controller acts for it. Beside four such
  machines, a run of 20 ms took 10 seconds.
- A step in a process of its own gives back at most 4 MiB and 1024 sends, and
  comes to at most 4 MiB with its state. Past that, that machine fails.
- On a host with less memory than four such steps hold, the host stops a step
  or the whole controller. The step is taken once more and its machine fails.
- A value is checked against a shape in time and memory that grow with the size
  of both, and nothing limits a shape. An owner's shape costs this to the
  controller. A made machine's shape, and a shape a `list:` gives, stop at the
  step's limits.

  a list of texts against items: { type: string }    0.07 microseconds a character
  256 KiB of numbers against 1800 types                119 seconds
  forty $refs that each name the next twice            never ends

These are true of sends and calls to addresses.

- A key is any text of at most 256 characters, and anyone who can list runs can
  read it.
- A run a send or a call starts counts as one level below its sender, and
  fails as it starts past its own file's `limits: { depth: }`, 16 by default.
- `limits: { runs: }` is counted as a send is made, so sends from several runs
  at once can pass it by a few.
- A run remembers the last message of each of its 64 most recent senders. A
  controller stopped while it sends, with 64 others heard before it resumes,
  can deliver an event twice.
- A controller stopped as it deletes an event no run takes writes no note of
  it in the sender's record.
- Anything about the sender in an event's data is only the sender's claim:
  `${event.from}` is what the controller wrote.

These are true of the store.

- A directory store keeps no process out. Every user of the computer who can
  read the directory can read and write all of it.
- Whoever operates the store can read every file path, delete any file and
  restore the store to an earlier state. They cannot read an encrypted file,
  and a file they alter is refused by its reader.
- Someone on the network between a served directory and a computer that uses
  it can see that the two communicate and how much data they exchange, and can
  delay or cut the connection. They can do nothing else.

Corbie makes no check where there is no real boundary.

`corbie manual permissions` has what is checked, and
`corbie manual the-store` has what is signed and encrypted.
