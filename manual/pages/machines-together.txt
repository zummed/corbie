Machines together: a job can be another machine, so a statechart can run a flow and an agent can use a flow as a tool.

The first two examples use `title.yaml` from `corbie manual first-machine`.
Record lines are shown without their time and run number, and `<id>` is a
run's ID.

A statechart runs the flow
--------------------------

    # watch.yaml
    statechart: watch-title
    initial: fetching

    states:
      fetching:
        job:
          machine: ./title.yaml
          input: { url: "https://example.com" }
        on: { done: finished }
      finished:
        end: done
        output: ${states.fetching.output.title}

    corbie test watch.yaml --watch
      step 1  <- start
      step 1  -> job fetching: a machine, <id>
      step 1  <- start {"url":"https://example.com"}
      step 1  -> job get_title: a script, on runner
      step 2  <- done from get_title {"title":"Example Domain","url":"https://example.com"}
      step 2  done
      step 2  <- done from fetching {"title":"Example Domain","url":"https://example.com"}
      step 2  done
      output: "Example Domain"

The job of the state `fetching` is the flow. The controller starts it as a
child run, whose lines are among the statechart's, with the child's run number.
When the child run ends, the statechart receives `done` with the flow's output and moves to `finished`.

An agent uses the flow as a tool
--------------------------------

    # helper.yaml
    agent: page-helper
    input: { question: string }
    model: { name: claude-haiku-5-5, secret: ANTHROPIC_KEY }
    prompt: ${input.question}

    tools:
      title:
        description: Give the title of a web page
        args: { url: string }
        job:
          machine: ./title.yaml
          input: { url: "${args.url}" }

    corbie test helper.yaml --input '{"question": "What is the title of the page at https://example.com?"}' --secret-env ANTHROPIC_KEY --watch
      step 1  -> job turn: a script, on runner
      step 2  -> job title: a machine, <id>
      step 1  -> job get_title: a script, on runner
      step 2  done
      step 3  <- done from title {"title":"Example Domain","url":"https://example.com"}
      step 3  -> job turn#2: a script, on runner
      step 4  done

`--secret-env ANTHROPIC_KEY` reads the model's API key from that environment
variable. Each turn is a job that calls the model. In the first turn the model
called the tool `title`, whose job is the flow, and in the second it answered.

As a job the flow keeps its own `allow:` list: the script may still connect
only to `example.com`.

A statechart sends to a run by its address
------------------------------------------

    # house/room.yaml
    statechart: room
    lifetime: keyed
    initial: open
    states:
      open:
        on:
          knock: open
          leave: closed
      closed: { end: done }

    # house/desk.yaml
    statechart: desk
    allow: [send:room, send:bell]
    initial: first
    states:
      first:
        entry:
          send:
            - { to: { at: room, key: "1" }, event: knock, data: { by: ana } }
            - { to: { at: room, key: "1" }, event: leave }
            - { to: { at: bell }, event: ring }
        timers: { pause: 1s }
        on: { pause: last }
      last: { end: done }

    corbie init --ceiling all --name laptop
    corbie start &
    corbie run submit house
      /house/desk   transient   recorded
      /house/room   keyed       recorded
    corbie run start /house/desk --watch
      step 1  <- start
      step 1  -> send knock to /house/room#1 · started <id>
      step 1  -> send leave to /house/room#1 · <id>
      step 1  -> send ring to /house/bell · undelivered: nothing is recorded at /house/bell
      step 2  done

`room.yaml` is keyed: it has a run for each key. The first send finds no run
with the key `1`, so it starts one, with the event's data as its input. The
second goes to that run, and nothing is recorded at `/house/bell`.

- `send:room` in `allow:` lets the statechart send to `/house/room`. A send it
  does not allow fails the statechart as `denied`.
- The run that takes a sent event reads its sender in `${event.from}`, and a
  send `to: "${event.from}"` replies. Of a job's `done` or `failed`, a timer or
  the parent's event, `event.from` is a name, and a send to it fails the
  statechart. A run hands out its own address as `${run.address}`.
- A send to `{ at }` of a transient location starts a new run of it, with the
  event's data as its input.
- A file's `receive:` lists who may send to its runs, by default every
  location of its tree and the tree's client.
- `limits: { runs: 50 }` in a keyed or transient file caps how many of its runs
  are running at once; a send that would start a run past it is not delivered.

An agent uses another team's tools
----------------------------------

Two teams share one controller, each a client with its own prefix. The
controller's owner enrols each with a ceiling: `at:` gives its prefix, and
`send:` lets the runs of `support` call the tools of `netops`. In this example
all three use one computer, and `--config` names each team's config.

    corbie client card --name netops --config ~/netops | corbie controller enrol - --ceiling 'at:/netops,secret:SWITCH_TOKEN@net:switch.example.com' | corbie client trust - --config ~/netops
    corbie client card --name support --config ~/support | corbie controller enrol - --ceiling 'at:/support,send:/netops/tools/*,secret:ANTHROPIC_KEY@net:api.anthropic.com' | corbie client trust - --config ~/support

`netops` writes a tool as a machine, sets its secret at the tool's location,
and submits it.

    # netops/tools/ports.yaml
    flow: ports
    description: Give the ports of a switch that are down.
    input: { switch: string }
    receive: [/support/triage]

    stages:
      read:
        job:
          script: ./ports.js
          input: { switch: "${input.switch}" }
          allow: ["secret:SWITCH_TOKEN@net:switch.example.com"]

    output: ${stages.read.output}

    // netops/tools/ports.js
    const token = secrets.get("SWITCH_TOKEN")
    const reply = http.get("https://switch.example.com/ports/" + input.switch, {
      headers: { Authorization: secrets.text`Bearer ${token}` },
      as: "json",
    })
    return reply.body.down

    corbie client secret set SWITCH_TOKEN --at /netops/tools/ports --env --config ~/netops
      taken
    corbie run submit netops --at /netops --config ~/netops
      /netops/tools/ports   transient   recorded

`support` gives the tool to its agent with `call:`.

    # support/triage.yaml
    agent: triage
    input: { question: string }
    model: { name: claude-haiku-5-5, secret: ANTHROPIC_KEY }
    prompt: ${input.question}

    tools:
      ports: { call: /netops/tools/ports }

    corbie client secret set ANTHROPIC_KEY --at /support/triage --env --config ~/support
      taken
    corbie run submit support --at /support --config ~/support
      /support/triage   transient   recorded
    corbie run start /support/triage --input '{"question": "Which ports of core-1 are down?"}' --watch --config ~/support
      step 1  -> job turn: a script, on laptop-runner
      step 2  -> job ports: a call to /netops/tools/ports, <id>
      step 3  <- done from ports ["ge-0/0/7"]
      step 3  -> job turn#2: a script, on laptop-runner
      step 4  done

- The model is shown the tool `ports` as
  `Give the ports of a switch that are down.`, with the argument `switch`.
  The agent reads both from the file when its run starts.
- The call is a run at `/netops/tools/ports`, with that file's `allow:`, the
  ceiling of `netops` and the secret set there. The agent gets its output.
- The ceiling of `support` holds no `SWITCH_TOKEN`, and no run at `/support`
  gets the secret.

`receive:` lists the one agent that may call the tool, so the client
`support` is refused:

    corbie run start /netops/tools/ports --input '{"switch": "core-1"}' --watch --config ~/support
      error: /netops/tools/ports does not receive a call from client:support
