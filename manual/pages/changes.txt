Changes: what to change in definitions, scripts and commands written for an earlier version.

Each section lists what changed after one release, the newest first.
`corbie version` prints the version of this binary. Nothing is kept backwards
compatible before version 1: a file or a command written the old way is
refused.

After 0.45.0
------------

Change a field that takes a list and is written as one text, which is refused:
`allow:`, `deny:`, a definition's `approve:`, `follows:`, `tags:`, `files:`,
`read:`, `receive:`, `defer:` and a model's `own:`.

  allow: net:example.com            allow: [net:example.com]
  receive: { stop: client:panel }   receive: { stop: [client:panel] }

Change a statechart in which a state's rule for `done` takes the `done` of a
state inside it. A state's `done` goes to that state only, and a holder's
rule for `done` is taken when a final state inside it is reached.

  open: { on: { done: shipped } }   working: { job: ./w.js, on: { done: shipped } }

Change a script that reads the ID `corbie run start` prints: the command waits
up to 15m by default for a controller to take the start, and prints the ID
then. A refused start prints `refused:` and the reason, and the command fails.
`POST /runs` waits the same way, and answers a refused start with
`{ "taken": false, "refused": "<reason>", "id": "<id>" }` and the status 200.

Change a flow's `when:` that reads a stage's `failed`, `error` or `skipped`
and relied on being skipped with that stage. A stage is skipped with a
skipped stage only when it reads that stage's output or emitted items, names
it in `follows:` or follows its emits; any other `when:` is evaluated, and a
skipped stage's `failed` reads false.

  when: ${!stages.ship.failed}   when: ${!stages.ship.failed && !stages.ship.skipped}

These are new.

- `corbie test <file> --in <directory>` refuses a tree in which a file has a
  problem, and prints each one, as `corbie up` does. Correct the file, or list
  it in `.corbieignore`.
- `corbie test <file> --in <directory> --definition` prints a definition read
  in its tree, as a definition with a `call:` entry needs.
- A script that returns or emits `NaN`, `Infinity`, a BigInt or a Symbol
  fails with status `error`. Return a number or text in its place.
- An expression whose value holds `NaN` or `Infinity` fails, as a script's
  value does. It gave null before. Read a field that may be absent as
  `${input.qty ?? 1}`.
- A step whose expressions fail reports every one, each with its place. It
  reported only one before.
- A call counts against `limits: { runs: }` in the step that makes it, as a
  send does: of two calls in one step to a location with `runs: 1`, the
  second fails with the reason.
- A flow's `output:` that reads a part a stage does not have, such as
  `${stages.fetch.done}`, is refused when the definition is checked. It
  read as null before. A stage has output, failed, error, status, skipped and
  emitted.
- `fs.list(dir)` with `fs.read:dir` gives every entry in `dir`; it gave only
  the entries the job could read before. With `deep`, it goes only into the
  directories the job may read, and `used:` lists each one.
- `corbie test` stops when no run has a job, a timer, a timeout or a ticket
  outstanding, prints each run still running, and fails: each waits on an
  event that nothing in its process sends. It waited until it was stopped.
- `corbie test` prints, after its run, each other run that failed and each run
  at a singleton or keyed location. With `--json` each run is a line of its own.
- A flow stage has the part `status`: the failed job's status, `error`,
  `timeout`, `denied` or `cancelled`, and null if the stage did not fail. A
  `when:` that reads it handles the failure, as `failed` does:
  `when: ${stages.live.status == 'timeout'}`.
- When the only stages that handle a flow's failure are skipped, the run's
  error names them: `bad: failed on purpose; the stage that reads it was
  skipped: handler`.

After 0.43.0
------------

This is new.

- A toolkit's tool is written `machine:` or `call:`, as an agent's entry is:
  `read_file: { call: gitlab/files/read, input: { project: group/orders } }`.
  Its description and arguments are the machine's, as `corbie manual toolkit`
  says.

After 0.42.0
------------

Change an agent's `toolkits:` and `list:` to entries of `tools:` that name a
toolkit, as `corbie manual agent` says.

  toolkits: { net: { include: toolkits/net/toolkit.yaml } }   tools: { net: { machine: ./toolkits/net.yaml } }
  the included file, with description: and tools:             a machine: add `toolkit: net` to it
  instructions: that read ${input…}                           the toolkit reads its own input, which the entry's input: gives
  a tool in a toolkit, called show                            the model calls it as net_show
  open { toolkit: net }                                       open { list: toolkits, name: net }
  approve: true on a toolkit, for its open                    approve: true on the entry, for its open and every call
  when: on a tool inside a toolkit                            when: on the entry
  hooks: for a toolkit's tools, in the agent                  unchanged for machine:; a toolkit at a location writes its own
  tools: { files: { list: …, job: … } }                       a toolkit whose job: answers every request, with open: true
  ${tool} in the job of an entry with list:                   input.request.tool, in the toolkit's job
  job.tool.entry and job.tool.name                            job.tool.toolkit and job.tool.name
  job.tool.description                                        gone
  a tool or a listed tool with a blob argument, in a toolkit  write the tool in the agent
  conversation.opened, a hash for each toolkit                the list of each toolkit that is open; no hash is checked
  the Toolkits page of `corbie ui`                            gone: a toolkit is a machine on the Machines page

- A call of a toolkit's tool that ends `{ working, state }` or
  `{ requests, state }` is shown to the model as a task, and the model
  carries it on with `resume`, as `corbie manual agent` says. No entry is
  named `resume`.
- A tool written under a toolkit's `tools:` may give `{ working, state }` or
  `{ requests, state }` in place of its result, and its job runs again for a
  resume or a cancel. A resume gives the tool's `args` again. A resume waits
  up to `limits: { resume: 10m }`.
- A toolkit takes `files:`, and then has the tool `read`: a skill is a
  toolkit whose instructions include its `SKILL.md`. A toolkit that names a
  tool `read` and writes `files:` is refused.
- `server.toolkit` gives the skills of an MCP server that has the Skills
  extension, each as a toolkit in the server's list, as `corbie manual mcp`
  says.
- A toolkit's list of more than 16 KiB is not offered: the result of `open`
  gives the names of its entries, and the model opens a tool by its name
  before it calls it. Names of more than 16 KiB, or that many toolkits, are
  a blob, which the model searches with the blob tools.
- `limits: { show: }` sets that size for an agent. `blob_read` and
  `blob_search` return the items that fit in it, with `next`.
- A toolkit's tool is given a blob: the model gives the name it was shown.
- In a carried conversation, an open list is `{ entry, entries, stored,
  blob }`.
- `open` and `resume` have the same description at every turn. The model is
  told which toolkits it can open in the conversation: before its prompt,
  and in the result of an open. A hook or a turn script that read the list
  from the description of `open` reads the conversation.
- `model: { tool_changes: true }`, for the service anthropic, keeps the
  service's cache when a toolkit is opened, as `corbie manual agent` says.
  `llm.chat` gives `offered`, which a turn script of your own keeps in the
  assistant part for it to work.
- An entry `{ machine: ./file.yaml }` names a machine by its file, as
  `{ call: location }` names one by its location.
- `toolkit:` is a fifth type of machine. It holds tools that any machine
  opens and calls with a job, by its file or by its location, as
  `corbie manual toolkit` says.
- `server.toolkit(request)` of the `mcp` plugin answers a toolkit's request
  for an MCP server, as `corbie manual mcp` says.

After 0.39.0
------------

Update the computers that serve a directory before its runners and clients. A
runner or a client stops waiting for a server that sends nothing for three
seconds, and a server of 0.39.0 sends nothing while it works on a request.

  corbie init store, on a member       prints a row for each member: its name, its address, and whether it leads
  corbie init store --json             has `name`, and `members`: each one's `name`, `address` and `state`
  corbie init store --listen fe80::…   refused: an IPv6 link-local address
  corbie start runner, with no trust   stays running, and takes jobs once corbie runner trust is run

A store with more than one member is made again. With no run in progress,
stop `corbie start` on every member and run `corbie init store --alone` on
one. The others join with empty directories, as
`corbie manual served-directory` says.

  corbie init store --join corbie://host:port   removed: --join takes what corbie init store --admit printed
  controller/identity, copied by hand           not needed: --admit prints it encrypted to the computer's card
  corbie init store --remove host:port          takes the member's name: --remove sw2
  corbie init store --listen, on a member       changes the member's address; before, refused

After 0.38.0
------------

`corbie init store` with no `--listen` keeps the address saved before. Before,
it saved `:8372` again. Write `corbie init store --listen :8372` for that.

After 0.34.0
------------

Change `ask:` to a hook, as `corbie manual hooks` says.

  ask: ./ask.js                           hooks: { approval: { before: ./ask.js, when: "${job.approve}" } }
  input.jobs, a list                      input.job, one job: the hook runs once for each held job
  input.asking.machine                    input.job.run.machine
  a job's asked: { tool, args, … }        input.job.tool: { name, args, … }
  return { approved: [names], note }      return { ok: true } or { ok: false, note }
  the nearest ask above a job             every hook above a job runs, the job's own machine's first
  a stage, state or tool named ask        allowed

`approve: true` and `approve: [exec]` mark a job, as before. A definition that
marks a job, with no `before` hook in it or a machine above it, is refused as
it starts. A marked job that no `before` hook's `when:` holds for fails with
status `denied`.

After 0.32.0
------------

Change the path of a run's output or input that is itself a blob.

  { "$blob": "file" }         the whole output; before, the path was empty and the gateway gave no bytes for it
  { "$blob": "input/file" }   the whole input; before, `input/`

`corbie run show <id> --save <dir>` saves it as `<dir>/file`.

After 0.31.0
------------

Change how the UI is started.

  corbie ui                 shows the machines the controller recorded, and reads no directory
  corbie ui --dir <dir>     removed: submit the directory with `corbie run submit`
  corbie ui controller      needed for Machines and Toolkits; a UI started as the client alone has Runs
  corbie ui with no store   refused: `corbie init` or `corbie up ui` sets one up

The Machines page shows no file's text and no problems: `corbie run submit`
and `corbie test` print a file's problems. A run's page says when a submit
changed the definition at its location since the run started.

After 0.30.0
------------

Change this command.

  corbie mcp                     the model may run every command of Corbie's
  corbie mcp --allow <command>   as before: the model may run only the commands named

After 0.29.0
------------

These are new.

- The gateway does everything a client does. New routes submit a tree, set,
  remove and list secrets and values, send an event to a location or a key,
  and give a run's tickets, one step and the files of its result:
  `corbie manual routes`.
- `corbie run …`, `corbie client secret …` and `corbie client value …` take
  `--gateway <address>`, and send the token in `CORBIE_GATEWAY_TOKEN`. A Go
  program makes such a client with `client.Remote`.
- A page in a browser calls a gateway from any origin, with the token in
  `Authorization`: `corbie manual gateway`.
- A gateway runs as an AWS Lambda function, called through the function's
  URL: `corbie manual functions`.
- A gateway acts as several clients: `gateway --client <config>`, once for
  each. A line of `--token-file` is a token, the client it names and the
  principal it was given to, a person or a service:
  `corbie manual gateway-clients`.
- A gateway takes the tokens of an OIDC issuer: `gateway --oidc-issuer` and
  `--oidc-audience`. A claim names the client and another the principal.
- `corbie client show` prints which client a command is sent as, and through a
  gateway the principal its token names.
- A run's record names the principal a client sent each message for, as
  `principal` in a `cause`.
- A machine reads the principal a client sent an event for as
  `event.principal`, and the principal a client started its run for as
  `run.principal`.

After 0.28.0
------------

These behave differently.

- A command with no `--config` and no `CORBIE_CONFIG` uses the config `.corbie`
  of the current directory, or of the nearest directory above it, before the
  one in the user's config directory.
- A directory named `.corbie` is not read as part of a tree.
- `corbie ui` takes a free port when 127.0.0.1:8373 is in use and `--listen`
  is not given.

These are new.

- `corbie up` sets up and runs a controller, a runner and a gateway on a
  directory of machines, in `.corbie` of the directory: `corbie manual a-project`.
- `corbie test --value-env NAME` sets a value from the environment variable.
- A program started beside a gateway has its address in `CORBIE_GATEWAY` and
  its token in `CORBIE_GATEWAY_TOKEN`.

After 0.27.0
------------

These behave differently.

- The UI is part of `corbie`. `corbie ui` and `corbie start controller runner
  ui` need no program `corbie-ui` on PATH: remove it.

These are new.

- `corbie add` writes a pack of ready-made machines into a project: `corbie
  manual packs`.

After 0.26.1
------------

These behave differently.

- A problem in a definition is printed with its line: `line 3: model.colour: …`
  in the definition's own file, and `kids/kid.yaml:2: value: …` in another.
  `--json` gives it in the same text. Before, a problem gave its file and place
  alone.

After 0.22.0
------------

Change these commands.

  corbie run submit <location>      corbie run start <location>, with the same flags
  corbie mcp --allow "run submit"   add --allow "run start" for a model that starts runs

`corbie run submit` records a file or a directory, and takes `--at` and a
script file's flags only.

These are gone.

- `handover:` on a singleton statechart. A singleton started again is given
  no input. A machine that must keep data across a change to its file writes
  it to a file of its own, with `fs.write:`, and reads it as it starts.

These behave differently.

- An `approve:` entry holds a job whose `allow:` entry of the same kind matches
  a value the `approve:` entry matches. Before, an `approve:` entry that began
  with `*`, as `net:*.internal`, held every job of its kind.
- `llm.chat` with no `service:` uses the service the model's name is of, and
  refuses a model no service claims. Before, it used `anthropic`.
- A program using the client package is given the error by `Watch` when a
  look fails after the first listing. Before, `Watch` went on.
- An agent's `conversation` names each toolkit open under `opened`, with the
  hash of its instructions: `opened: { net: "9f86d0…" }`. An agent given it
  opens each of them whose `when:` holds, that has no `approve: true`, and
  whose instructions are unchanged, and the model is shown its tools from the
  first turn.
  Before, it opened none. A `system:` text that tells the model to open a
  toolkit again in each run can go.

These are new.

- `corbie controller enrol` and `corbie runner trust` take `--at <prefix>`
  for a runner, once for each prefix. The runner is sent, and takes, only the
  jobs of runs at or under its prefixes. A runner enrolled with no `--at` is
  sent the jobs of every tree, as before.
- `corbie client secret set|remove|list` and `corbie client value
  set|remove|list` set a client's secrets and values in its own trees, by
  `--at`. Before, only the controller's owner set them.
- `usage` from `llm.chat`, and an agent's `tokens`, hold `cached`: how many
  of `input` the model's service read from its cache.

These are new, and make a definition shorter.

- A flow of one stage with no `output:` gives that stage's output, so
  `output: ${stages.<name>.output}` can go. Before, it gave no output. A
  stage with `each:` keeps its flow's `output:`.
- A `secret:` entry allows its destination. `allow: ["secret:KEY@net:host"]`
  is enough, and `net:host` beside it can go. `secret:KEY@*` allows no
  destination.
- An `at:` entry in a client's ceiling allows sends to every location at or
  under its prefix. `send:/work/**` beside `at:/work` can go.
- A state with no job may give `output:`. The value is filled in as the state
  is entered and is the state's output, and the state is then given `done`.
  It replaces a script job that only returns a value, and a final state
  inside a state that only gives the outer state an output.
- The gateway's `POST /runs` takes JSON when the input has no file.
- A stream of the gateway ends with an `error` event when the gateway could
  not read the store.
- An agent's tool written `call:` takes a location in another tree, written
  from `/`, as `call: /netops/tools/show`. Its description and arguments are
  read from the machine there when the run starts. It replaces a tool
  written with `description:`, `args:` and `job: { call: … }` for that
  location.
- `decision:` is a fourth type of machine. It puts questions to a decision
  model and gives the probability of each answer, with no script and no
  `allow:` entry. It replaces a script that only calls `llm.decide`.
