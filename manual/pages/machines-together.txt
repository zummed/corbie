Machines together: a job can be another machine, so a statechart can run a flow and an agent can use a flow as a tool.

The first two examples use `title.yaml` from `corbie manual first-machine`.
Record lines are shown without their time and run number, and `<id>` is a
run's ID.

A statechart runs the flow
--------------------------

    # watch.yaml
    statechart: watch-title
    initial: fetching

    states:
      fetching:
        job:
          machine: ./title.yaml
          input: { url: "https://example.com" }
        on: { done: finished }
      finished:
        end: done
        output: ${states.fetching.output.title}

    corbie test watch.yaml --watch
      step 1  <- start
      step 1  -> job fetching: a machine, <id>
      step 1  <- start {"url":"https://example.com"}
      step 1  -> job get_title: a script, on runner
      step 2  <- done from get_title {"title":"Example Domain","url":"https://example.com"}
      step 2  done
      step 2  <- done from fetching {"title":"Example Domain","url":"https://example.com"}
      step 2  done
      output: "Example Domain"

The job of the state `fetching` is the flow. The controller starts it as a
child run, whose lines are among the statechart's, with the child's run number.
When the child run ends, the statechart receives `done` with the flow's output and moves to `finished`.

An agent uses the flow as a tool
--------------------------------

    # helper.yaml
    agent: page-helper
    input: { question: string }
    model: { name: claude-haiku-5-5, secret: ANTHROPIC_KEY }
    prompt: ${input.question}

    tools:
      title:
        description: Give the title of a web page
        args: { url: string }
        job:
          machine: ./title.yaml
          input: { url: "${args.url}" }

    corbie test helper.yaml --input '{"question": "What is the title of the page at https://example.com?"}' --secret-env ANTHROPIC_KEY --watch
      step 1  -> job turn: a script, on runner
      step 2  -> job title: a machine, <id>
      step 1  -> job get_title: a script, on runner
      step 2  done
      step 3  <- done from title {"title":"Example Domain","url":"https://example.com"}
      step 3  -> job turn#2: a script, on runner
      step 4  done

`--secret-env ANTHROPIC_KEY` reads the model's API key from that environment
variable. Each turn is a job that calls the model. In the first turn the model
called the tool `title`, whose job is the flow, and in the second it answered.

As a job the flow keeps its own `allow:` list: the script may still connect
only to `example.com`.

A statechart sends to a run by its address
------------------------------------------

    # house/room.yaml
    statechart: room
    lifetime: keyed
    initial: open
    states:
      open:
        on:
          knock: open
          leave: closed
      closed: { end: done }

    # house/desk.yaml
    statechart: desk
    allow: [send:room, send:bell]
    initial: first
    states:
      first:
        entry:
          send:
            - { to: { at: room, key: "1" }, event: knock, data: { by: ana } }
            - { to: { at: room, key: "1" }, event: leave }
            - { to: { at: bell }, event: ring }
        timers: { pause: 1s }
        on: { pause: last }
      last: { end: done }

    corbie init --ceiling all
    corbie start &
    corbie run submit house
      /house/desk   transient   recorded
      /house/room   keyed       recorded
    corbie run submit /house/desk --watch
      step 1  <- start
      step 1  -> send knock to /house/room#1 · started <id>
      step 1  -> send leave to /house/room#1 · <id>
      step 1  -> send ring to /house/bell · undelivered: nothing is recorded at /house/bell
      step 2  done

`room.yaml` is keyed: it has a run for each key. The first send finds no run
with the key `1`, so it starts one, with the event's data as its input. The
second goes to that run, and nothing is recorded at `/house/bell`.

- `send:room` in `allow:` lets the statechart send to `/house/room`. A send it
  does not allow fails the statechart as `denied`.
- The run that takes an event reads its sender in `${event.from}`, and a send
  `to: "${event.from}"` replies.
- A file's `receive:` lists who may send to its runs, by default every
  location of its tree and the tree's client.
- `limits: { runs: 50 }` in a keyed file caps how many of its runs are
  running at once; a send to a new key past it is not delivered.
