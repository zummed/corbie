Agent: an agent calls an AI model in a loop, runs the tools the model calls, and ends when the model answers without calling a tool.

Each call to the model is one turn, and each tool is a job. An agent ignores
events sent to it.

    # librarian.yaml
    agent: librarian
    input: { dir: string, question: string }
    model: { name: claude-sonnet-5-5, secret: ANTHROPIC_KEY }
    system: You answer questions about a library of files.
    prompt: ${input.question}

    tools:
      shelf:
        description: Give back every file on one shelf
        args: { shelf: string }
        job:
          script: ./shelf.js
          input: { dir: "${input.dir}", shelf: "${args.shelf}" }
          allow: ["fs.read:${input.dir}/**"]

    // shelf.js
    return fs.list(input.dir + "/" + input.shelf).map((file) => file.name)

    corbie test librarian.yaml --input '{"dir": "/srv/books", "question": "What is on the top shelf?"}' --secret-env ANTHROPIC_KEY --watch
      step 1  -> job turn: a script, on runner
      step 2  -> job shelf: a script, on runner
      step 3  <- done from shelf ["dune.txt","emma.txt"]
      step 3  -> job turn#2: a script, on runner
      step 4  done

Fields
------

  model           the model, needed even when a `turn:` script calls none
  system          the system prompt, which may hold `${input...}`
  prompt          the first message to the model, an expression of the input
  tools           the entries, by name: tools, and machines that are tools
                  or toolkits
  reply           a shape, as under Tools: the reply is data in this shape
  conversation    the `conversation` of an earlier agent's result: this agent
                  continues it, and each blob keeps its name
  turn            a script that makes each turn in place of Corbie's own, as
                  in `corbie manual agents`; with one that calls no model, and
                  no `secret:`, `corbie test` runs the tools with nothing set up

`limits: { turns: 20 }` is the number of turns, default 20. At the limit the
agent fails with `turn limit reached`. Its error's output holds the
`conversation`, and another agent given it as `conversation:` carries on.

The model
---------

  name            the model's name, as its service knows it
  secret          the name of the secret that is the service's API key
  service         anthropic, openai (the Responses API), openai-chat (the
                  Chat Completions API) or claude-code; by default anthropic
                  for a name that begins claude, and openai for gpt, o1, o3
                  and o4
  address         the URL of a service that has the same API somewhere else:
                  a self-hosted model, or one that a cloud offers
  effort          low, medium or high; claude-code also takes xhigh and max
  reply_tokens    the most tokens a reply may hold
  own             for claude-code: tools of the program that the model may use
  tool_changes    for anthropic: `true` keeps the service's cache when a
                  toolkit is opened, as under Toolkits

The key is a secret. `--secret-env ANTHROPIC_KEY` reads it from that
environment variable for `corbie test`, and `corbie controller secret set
ANTHROPIC_KEY` sets it for every tree. Each turn's job gets `net:<host>` for the
service and `secret:<secret>@net:<host>`, and nothing from the definition's
`allow:`.

    # elsewhere.yaml
    agent: elsewhere
    model: { name: my-model, service: openai-chat, address: https://models.example, secret: MODELS_KEY }
    prompt: Say hello.

    corbie test elsewhere.yaml --secret-env MODELS_KEY
      output: {"conversation":{"blobs":{},"turns":[{"$blob":"conversation.turns[0]","size":1714,"type":"application/json"}]},"reply":"Hello.","tokens":{"cached":0,"input":10,"output":5}}
      used: net:models.example:443 secret:MODELS_KEY@net:models.example:443

The result
----------

  reply           the model's last reply, as text or in the shape of `reply:`
  tokens          { input, output, cached }, counted over the agent's own
                  turns; cached is how many of input the service read from
                  its cache
  conversation    { turns, blobs, opened, tasks }: a blob for each turn, each
                  blob the model was shown by its handle's name, the list of
                  each toolkit that is open, and each call that has not ended

A reply that does not fit `reply:` is returned to the model, which takes
another turn. A failed agent's output has `conversation` and `tokens`.

Tools
-----

`tools:` holds entries, by name. An entry is a tool written in place, or a
machine named by its file or by its location.

  description  what the tool is for, in plain text with no expression: the
               model chooses a tool by this text
  args         the shape of its arguments: { name: type }, or JSON Schema
  job          `script:`, `machine:`, `call:` or `send:`, as in
               `corbie manual definitions`; it reads `input`, the agent's
               input, and `args`, the model's arguments
  machine      the file of a machine, in place of `description:`, `args:`
               and `job:`
  call         the location of a machine, in place of `machine:`
  input        with `machine:` or `call:`, the names of that machine's input
               the entry fixes
  approve      with `machine:` or `call:`, `true` marks every job the entry
               starts for approval
  meta         with `machine:` or `call:`, data hooks read as `job.meta`
  open         with a toolkit, `true` opens it before the first turn
  when         a condition on the agent's input, checked when the run
               starts: the entry is offered only if it holds

A shape is written as `input:` is, in `corbie manual definitions`:
`args: { shelf: string, limit: "number?" }`. A name the shape does not give is
refused, and a blob is the name the model was shown.

A shape written with `type: object` is JSON Schema, which can give an argument
a `description`, an `enum` or fields of its own. `format: blob` marks a blob at
any depth.

- A tool whose job has `approve: true` starts only after a `before` hook, as
  `corbie manual hooks` says. A hook reads the call as
  `job.tool: { name, args, said }`: the tool's name, the model's arguments
  and the model's text. A call a hook refuses is returned to the model as
  denied, with the hook's note.
- A tool whose job fails is returned to the model as an error.
- A tool whose job is an agent is a sub-agent. The model gets the sub-agent's
  reply, and the sub-agent's conversation stays in its own record.
- A tool whose job is a call gets the called run's whole result, or its error.
- A tool called twice in one turn has jobs named `shelf` and `shelf.1`.
- No entry is named turn, preview, open, resume, toolkits, blob_read,
  blob_search or blob_code.

A machine as an entry
---------------------

An entry written `machine:` or `call:` takes its description from the machine
it names. A toolkit makes the entry a toolkit, as under Toolkits. Any other
machine makes it one tool, whose arguments are the machine's input.

  machine: ./summary.yaml    the machine's file: a child run of the agent
  call: gitlab/files/read    a location in the same tree, read when the tree is read
  call: /netops/tools/show   a location in any tree, read when the run starts

  tools:
    read_file: { call: gitlab/files/read, input: { project: group/orders } }

  gitlab/files/read.yaml:
    flow: read
    description: Read one file of a project.
    input: { project: string, path: string, ref: "string?" }

The model is shown `read_file` as `Read one file of a project.`, with the
arguments `path` and `ref`. A call `{ path: a.txt }` starts a run of
`gitlab/files/read` with the input `{ project: group/orders, path: a.txt }`.

- The arguments are the machine's `input:` without the names the entry fixes.
  The model giving any other name does not fit.
- An argument the model leaves out is absent from the machine's input.
- `input:` may read the agent's input, as `${input.team}`.
- An entry written `call:` has `send:` for the location, and nothing else is
  written for it.
- The machine has a `description:`. One at a location is transient, and a
  file `.corbieignore` lists is no machine.
- A machine that is an agent is shown to the model as its reply.
- An entry written `call:` is refused in a machine made while running. One in
  the same tree is refused in a file read alone.

A location written from `/` is read at the run's start, where a call from
the run would pass: `send:` in every layer, the client's ceiling included,
and the machine's `receive:`. A run keeps what it read, so a change
submitted there reaches the next run. When the entry is offered and the
machine cannot be read, the agent fails at its start with the reason.

A tool written in place runs at the agent's location, so its secret can be
set no narrower than the agent. A tool that uses a secret is a machine at a
location of its own, named with `call:`, with the secret set there, as
`corbie manual machines-together` shows. A tool that uses no secret is
written in place: one file and one run fewer.

Toolkits
--------

A toolkit is a machine that holds tools, as `corbie manual toolkit` says. An
entry that names one gives the model its tools once the model opens it, so an
agent with many tools shows the model the ones it has opened.

  tools:
    net:    { machine: ./toolkits/net.yaml, input: { asker: "${input.asker}" } }
    github: { call: tools/github, open: true }
    orders: { call: /orders/toolkits/orders, approve: true }

1. The model is shown a tool `open`, and before its prompt the list
   `toolkits`: the name and the description of each toolkit it can open.
2. The model calls `open` with `{ list: toolkits, name: net }`, and a job
   named `open` runs the toolkit with the request `{ do: open }`.
3. `open` returns the toolkit's instructions to the model.
4. From the next turn, the model is shown the toolkit's tools, each as the
   entry's name, `_` and the tool's name: `net_show_status`.
5. A call of `net_show_status` runs the toolkit with the request
   `{ do: call, tool: show_status, args }`, and returns its result.

  machine: ./toolkits/net.yaml   child runs of the agent, with the agent's secrets and hooks
  call: tools/github             runs at that location, with its secrets and its hooks

- The entry's `input:` is the toolkit's input. The agent adds `request`.
- The toolkit checks the arguments. Arguments that do not fit are returned to
  the model as an error. The agent gives a toolkit's tool no blob: a name the
  model was shown is sent as the text it is.
- With no instructions, `open` returns `Opened net.`.
- In a tool's name, characters other than letters, digits, `_` and `-`
  become `_`.
- An open that gives a tool whose name another tool has, or a name longer
  than 64 characters, is returned to the model as an error.
- `open: true` opens the toolkit before the first turn, with a job named
  `open`. The first turn is offered its tools and shown its instructions. A
  toolkit that fails to open then fails the agent.
- `approve: true` marks the open and every call for approval. A hook reads
  `job.tool: { toolkit, name, args, said }`, where `toolkit` is the entry's
  name, and for an open `{ toolkit, open: true, said }`. An open a hook
  refuses opens nothing.
- The agent's hooks run for the open and for each call. A toolkit's own
  `hooks:` run for its tools' jobs.
- A toolkit's list may hold a toolkit. The result of `open` names it, the
  model opens it with the list's name, `{ list: github, name: review }`,
  and its tools are shown as `github_review_read`.
- A toolkit's list larger than `limits: { show: }` is not offered. The result
  of its `open` gives the names, `{ kind, name, description }`, and the model
  calls `open` with the list and an entry's name. A job named `open` reads
  the entry, and a tool is offered from the next turn.
- Names larger than the limit are a blob, as is a list `toolkits` that
  large. The model searches it with the blob tools, then opens an entry.
- A toolkit's tool takes a blob as a tool written in place does: `args: {
  file: blob }` is offered as a name, and the tool's job reads the blob.
- An agent given a `conversation` has open each toolkit in its `opened`
  that the agent has, whose `when:` holds and that has no `approve: true`.
  It runs no open for it, and gives no instructions again. The model opens
  any other toolkit with `open`.

A toolkit answers a call with `{ working, state }` where the work goes on,
such as a task of an MCP server, or `{ requests, state }` where it needs
input. The call is then a task.

1. The model is shown `{ task: task1, working }` or `{ task: task1, requests }`.
2. The model is offered a tool `resume`, and goes on with other tools.
   A call's result names its task.
3. The model calls `resume` with `{ task: task1 }`, and a job named `resume`
   runs the toolkit with the request `{ do: resume, tool, args, state }`.
4. The toolkit waits for the work, and `resume` returns its result.

- `resume` takes `responses`, by the names of the requests, for a call that
  asked for input, and `cancel: true` to cancel the call.
- A resume that returns `working` again keeps the task.
- A resume has the entry's `approve:`. A hook reads `job.tool: { toolkit,
  name, args, resume, requests, responses, cancel }`, where `resume` is the
  task's name, and gives other responses with `{ ok: true, input }`.
- A resume a hook refuses keeps the task. One that fails ends it.
- An agent that ends with a task working gives it in `conversation.tasks`,
  and an agent given that `conversation` resumes it.

The service's cache
-------------------

A model service keeps the start of a request in its cache and charges less
to read it again. The tools are at the start, so by default every open, and
every tool opened from a long list, loses the cache for the turn after it.

  model: { name: claude-sonnet-5-5, secret: ANTHROPIC_KEY, tool_changes: true }

1. The tools sent to the service stay those of the first turn.
2. A tool that an open adds, or that is no longer offered, is sent as a
   message of the conversation.
3. Every turn after the first reads the earlier turns from the cache.

- Only the service anthropic takes `tool_changes:`. For any other service
  the definition is refused.
- The model must take it: Opus 4.8 and later, Sonnet 5.5, Haiku 5.5, and the
  Fable and Mythos models, at Anthropic's own API. Any other model refuses
  the request, and the turn fails with the service's message.
- `tokens.cached` in the result is how many tokens the service read from its
  cache.
- A `turn:` script of the definition's own keeps `offered` with each reply
  for this to work, as `corbie manual agents` says.
- `open` and `resume` have the same description at every turn, with or
  without `tool_changes:`.

Who is offered what
-------------------

A `when:` on an entry is checked once, when the run starts, on the agent's
input.

- `open` does not name a toolkit whose `when:` does not hold, and a call of
  `open` with its name is returned to the model as an error.
- A tool whose `when:` does not hold is not shown, and a call of it is
  returned to the model as an error.
- A `when:` that cannot be evaluated fails the agent before its first turn.
- `open` and the blob tools take no `when:`.

Blobs
-----

- The model gets a blob as a handle, `{ blob: "blob1", type, size, items,
  cost, preview }`, and gives the name `blob1` where a tool's `args:` has the
  type blob or `format: blob`.
- `items` counts its lines, rows or entries, `cost` estimates the tokens
  needed to read it, and `preview` is its first items, given once.
- Every agent has the tools `blob_read`, `blob_search` and `blob_code`, which
  read part of a blob. A large answer from one is returned as a blob.
- A tool's result over 32 KiB is stored as a blob by a job named
  `preview`, which also reads each new blob before the next turn.
- `limits: { show: 4KB }` changes that size, for a model with a small
  context. `blob_read` and `blob_search` return the items that fit in it,
  with `next`, the item to continue from.
- A blob with no items, such as a document or an image, needs a tool of the
  definition's that reads its format.
- An image or a PDF that the service accepts is also sent to the model whole.

Claude Code
-----------

`service: claude-code` starts the `claude` program on the runner's computer
for each turn, in place of a request to a service. It takes no `address:` and
no `reply_tokens:`.

    # searcher.yaml
    agent: searcher
    model: { name: sonnet, service: claude-code, own: [WebSearch, WebFetch] }
    prompt: Say hello.

    corbie test searcher.yaml
      used: env:HOME exec:claude network

- With no `secret:`, the program is signed in as the runner's user, and the
  turn's job gets `exec:claude`, `env:HOME` and, for a runner on Windows,
  `env:USERPROFILE`. With `secret:`, the job gets `exec:claude` and
  `secret:<secret>@exec:claude`.
- The program starts with none of its own tools, no saved session and none of
  its user's settings, so the model's tools are the definition's.
- Corbie does not run a tool named in `own:` and cannot limit it to a scope,
  so it needs a whole group allowed in every layer of permission, the
  ceilings included. Each use is written to the record as an emitted value
  named `own`.

  network    WebSearch and WebFetch
  disk       Read, Glob, Grep, Edit, Write and NotebookEdit
  all        Bash, Skill and any other tool; Skill also loads what the
             runner's user has set up for the program
