Definitions: every type of machine shares these fields, expressions, jobs, events and hooks.

A definition is a YAML file. One field gives the machine's type and name:
`flow: digest`, `statechart: review`, `agent: librarian` or
`decision: urgent`. It may be written anywhere in the file, or come from a file it includes. A name is letters,
digits, `_` and `-`, and starts with a letter.

Fields every type takes
-----------------------

  description: Sums a list.    what the machine is for, in plain text with no expression
  input: { urls: list }        the shape of a run's input, as below
  keep: 7d                     how long an ended run, and each step and log line of a running run, is kept; default 7d
  limits: { timeout: 1h }      how much a run may use, as below
  allow: [net:example.com]     permissions of every script job in the definition
  deny: [exec]                 what no script job in the definition may do
  approve: [disk]              permissions that mark a job for approval
  hooks: { small: { before: ./small.js } }    jobs that run before or after other jobs, as below
  title: "${input.topic}"      a run's title, filled in when it starts, as below
  meta: { owner: alice }        data Corbie keeps and never reads; no expression in it is filled in
  lifetime: singleton          how runs start at the file's location, as below
  update: restart              what a changed file does to its runs, as below
  receive: [client:panel]      who may send to its runs or call it, as below
  read: [client:wall]          other clients that read its runs, as below

`title:` names a run to a person, and `corbie run show` prints it. Its
expressions read `input`, `values` and `run`.

- A title is one line of at most 200 characters. Each run of white space,
  line breaks among it, becomes one space, and a longer title is cut.
- Only the clients that read the run's record see its title. `corbie run ls`
  does not print it.
- A title that cannot be filled in fails the run, as an input that does not
  fit does.

`limits:` takes these.

  timeout: 1h    how long a run may take; default no limit
  depth: 16      levels of child runs below a run that a client or a submit started; default 16, 0 for none
  jobs: 100      how many jobs a run may start; default no limit
  runs: 50       of a keyed or transient file, how many runs at its location may be running at once; default no limit
  turns: 20      an agent's turns, as in `corbie manual agent`

A length of time is written `30s`, `5m`, `48h` or `7d`.

Include
-------

A definition can take values from other files with `include:`, which names a
file or a list. A name may end in `#path` to take one part of a file.

  agent: family
  include: ./base.yaml                       merges in base.yaml's fields
  model: { effort: high }                    merged with base.yaml's model
  system:
    - { include: ./style.md }                a text of pieces, joined by one empty line
    - You look after one house.
  allow:
    - { include: ./base.yaml#allow }         base.yaml's allow: list, item by item
    - net:devices.lan

1. The client reads each file when it submits the tree.
2. In a mapping, it merges in the included fields at every depth.
3. In a list or a text, it replaces `{ include: <file> }` with the file's list
   or text, and `{ include: <file>#<path> }` with the value at that path.
4. The stored definition holds no `include:`, and keeps each value's file and
   line.

- A value the file writes wins over an included one. A list or a text it
  writes replaces the included one whole.
- To take only part of a file, name each part with `#path`.
  `tools: { read: { include: ./tools.yaml#read } }` takes one tool, and a tool
  added to tools.yaml later does not reach it.
- A file's values win over those of the files it includes, and an earlier
  file's over a later one's.
- A file may take its type and name from a file it includes, as
  `include: shared/post.yaml` does. A type it writes itself is the same type,
  and its name wins.
- `${…}` in an included text is an expression. A literal `${` is written
  `${'${'}`.
- A path in a file is read from the context, and a path starting `./` from
  that file's directory, as for a job.
- `input:` and `meta:` stay as they are written: an `include:` in them is not
  read. A script reads a file with `require`, as `corbie manual scripts` shows.
- A problem in a file names the file.
- More than 1,000 includes written out by one definition are refused. A file
  reached by two routes counts each time, though its values are merged once.
- `corbie test <file> --definition` prints the definition written out, each
  value with its file and line, and runs nothing.

Input
-----

`input:` is the shape of a run's input: each name, with the type of its value.

  string, number, boolean    that JSON type
  list, map                  an array, an object
  blob                       a blob, such as a file given with --input-file
  any                        any value
  ? after the type           the name may be left out; inside { } YAML needs it in quotes

The controller checks the input when the run starts.

1. It fills in each missing name that has a `default`.
2. It checks the input against `input:`.
3. A run whose input does not fit fails, and the error names each place.

A shape written with `type: object` is JSON Schema, which can give a `default`.

    # look.yaml
    flow: look
    input:
      type: object
      properties:
        url: { type: string }
        depth: { type: number, default: 2 }
      required: [url]
    stages:
      it:
        job: { script: ./echo.js, input: "${input}" }
    output: ${stages.it.output}

    // echo.js
    return input

    corbie test look.yaml --input '{"url": "https://example.com"}'
      output: {"depth":2,"url":"https://example.com"}

- A name that `input:` does not give is taken as it is, and a name the input
  does not hold reads as `null`. A definition with no `input:` takes any input.
- A default is filled in the input and in each object that `properties` and
  `items` lead to. A `default` elsewhere, such as under `anyOf` or behind a
  `$ref`, is refused.
- A `$ref` resolves only within its own shape.
- A shape may lead back to itself with `$ref`, and so describe a tree. A value
  checked against a `$ref` that leads back with no part of the value between
  fails.

Values and expressions
----------------------

An expression is one JavaScript expression between `${` and `}`. Any value may
contain one.

  count: "${input.n}"                  exactly one expression: its value, of any type
  text: "Look into ${input.topic}."    text with each value filled in
  n: 3                                 anything else is literal
  when: ${input.n > 1}                 a condition: exactly one expression

An expression reads these names.

  input                     the run's input, in every type
  values                    the values set at the run's location or above, as `values.HUB`
  run                       the run's `id`, `location`, `key`, `address`, `context` and `tree`, in every type
  stages, item              in a flow
  states, event, tickets    in a statechart
  args                      in an agent's tool

It may use JavaScript's operators, `? :`, arrow functions, methods such as
`map` and `filter`, and objects such as `Math`, `JSON`, `Date`, `Object`,
`Array`, `String`, `Number`, `RegExp`, `Map` and `Set`.

- A name that is not one of these is refused when the definition is checked.
- `when:` is a condition on a flow's stage, a statechart's transition, and an
  agent's toolkit or tool.
- An expression cannot change what it reads. It has no `eval`, `Function`,
  `Promise`, `require` or plugins, so it reads no file and makes no
  network connection.
- `Date` gives the time of the step, in UTC, and `Math.random` gives the same
  numbers each time the step is taken.
- An expression may run for one second. That limit stops its own code, and
  not a call to something built in that is under way.
- In a permission's scope an expression reads `input` and `values` and nothing
  else.
- A value is read by its name. `values[name]` and `values` alone are refused.
- An expression that reads a value not set at the run's location or above
  fails, naming the value and the location.
- Put a value that contains `${...}` in quotes when it is inside `{ }` or `[ ]`,
  or when the expression has a colon followed by a space.
- These take no expression: a name, a type, a permission's kind, a secret's
  name, a `deny:` or `approve:` entry, a description, a tag and a ticket's name.

Jobs
----

A machine contains jobs. A job is a script, a machine, or a send. A machine is
named by its file (`machine:`) or by its location (`call:`), and a send
delivers an event and returns nothing. A runner executes a script; a machine
named by its file runs as a child run, and one named by its location as a run
of its own whose result is the job's output.

  script: ./fetch.js           a script file
  machine: ./child.yaml        a definition file, or a definition written in place
  send: { to, event, data }    an event sent to a run by its address
  call: { at: services/weather }    a transient location whose run the job starts and waits for
  input: { url: "${item}" }    the input of the script, the child run or the called run
  allow: [net:example.com]     for a script, what the job may do, with the definition's `allow:`;
                               for a machine, a limit on everything the child run does
  deny: [fs.write:/etc/**]     what the job may not do
  timeout: 5m                  for a script, how long it may run, default 5m;
                               for a machine, the child run's timeout
  restart: { limit: 2 }        what happens when the job ends, as below; with none it runs once
  approve: true                marks the job for approval: it starts only after a `before` hook
  meta: { team: orders }       data hooks read as `job.meta`, and nothing else reads
  files: [./lib.js]            script only: files the script loads with require("./lib.js")
  memory: 256MB                script only: the most memory it may use, in B, KB, MB or GB
  tags: [gpu]                  script only: the job goes to a runner that has every tag

  job: ./fetch.js                                         short for job: { script: ./fetch.js }
  job: { machine: "${stages.make.output.definition}" }    exactly one expression in place of a path

- The context is the directory you submit as a tree. For a single file it is
  the directory you submit from, or the file's own directory for a file
  outside it. Every file is in the context, or below it.
- A path is read from the context, and a path starting `./` from the directory
  of the file it is written in: a definition, a machine kept in its own file,
  or an included file. `../` is refused.
- A script that loads another with `require` names it from its own directory,
  with `./` or `../`.
- A machine file or an included file that names a file already being read is
  refused: no file leads back to itself.
- A machine as it is stored is at most 4 MiB.
- A YAML alias cannot contain itself. A file whose aliases make more than about
  100 times what it writes, past 1000 values, is refused.
- A child run whose job has no `allow:` has what its own definition allows.
- An expression in place of a path evaluates to a blob that contains a
  script, or to a definition that a script made with `machines.define`.
- Each step of a machine made while running, and of everything below it, runs
  in a process of its own and may use 10 seconds and 1 GiB of memory. Past
  either, that machine fails with an error and nothing else does.

Restart
-------

A job with `restart:` runs again when it ends. With none it runs once.

  job:
    script: ./fetch.js
    restart: { after: always, limit: 5 in 1h, delay: 1s to 5m }

  after: failure       restarts after an error or a timeout; the default
  after: always        restarts after the job ends well too
  limit: 3             at most three restarts; no limit by default
  limit: 5 in 1h       at most five in any hour
  delay: 1s to 5m      doubles from the first to the second; the default
  delay: 30s           the same each time

- The job restarts with the input it was first given, and a machine as a new
  child run, from its start.
- A denial and a cancel are never restarted, so a job cancelled by hand stays
  stopped.
- A delay that doubles starts again once an attempt has stayed up for twice its
  longest wait.
- The machine sees only the final outcome: the last attempt's, past the limit.
  The run's record shows each attempt.
- Every value an attempt emits is delivered, so a job that repeats itself
  delivers its values again.
- With `after: always` and no limit, the machine sees no outcome, so a stage
  waiting on the job never ends.
- A restart after a failure is the same job: its `before` hooks do not run again.
- A restart after a job ended well is a new job: its `before` hooks run again,
  it has a new `job.request`, and it counts against `limits: { jobs: }`.
- A hook's job that ends well is final, whatever its policy says.

Locations
---------

Each *.yaml in a submitted directory has a location: its path under the prefix
it was submitted at, without `.yaml`. A file that `.corbieignore` lists has
none, as `corbie manual a-directory` shows.

  lifetime: singleton    one run, started by the submit
  lifetime: keyed        one run for each key a send names; statecharts only
  lifetime: transient    a new run for each call, start or send; the default

  update: restart        a changed file cancels the runs at its location
  update: drain          they finish on the definition they started with; the default

- A singleton always restarts, and `update: drain` on one is refused.
- `limits: { runs: 50 }` on a keyed or transient file caps how many runs at its
  location are running at once. Past it a send that would start a run is not
  delivered, a call fails, and a client's start is refused.
- A machine written in place or made while running has no location, and
  refuses `lifetime:`, `update:`, `receive:`, `read:` and `runs:`.

Sending and calling
-------------------

A job sends an event to a run by its address, or calls a location and waits
for the result.

  { at: devices/boiler }                    the run of a singleton location
  { at: services/report }                   a new run of a transient location
  { at: rooms/thermostat, key: kitchen }    the run for that key, started if none is running
  { at: devices/boiler, run: <ID> }         one run by its ID

  job: { send: { to: { at: devices/boiler }, event: set, data: { target: 12 } } }
  job: { call: { at: services/weather }, input: { days: 2 } }
  send: { to: "${event.from}", event: applied }    a reply to the sender

- A location is read from the tree's prefix, or in full when it starts with
  `/`. A name in it is not empty, `.`, `..` or `+`, and holds no `#`,
  backslash or control character.
- `at`, `key` and `run` may hold expressions, and `to` may be one expression
  that gives an address. The address is checked once it is filled in.
- A send job ends `done` once the event is written. It takes `to`, `event`,
  `data`, `approve`, `meta`, `allow` and `deny`, and nothing else.
- A call job's output is the called run's result. It fails if the receiver
  refuses it, if the location is not transient or is at its `limits: { runs }`,
  or if the run fails.
- A call job takes `call`, `input`, `timeout`, `restart`, `approve`, `meta`,
  `allow` and `deny`. Its `timeout` is the called run's, and each restart calls again.
- The called run belongs to its own tree's client. Cancelling the call job
  cancels it.
- A key is any text of 1 to 256 characters. Anyone who can list runs can read
  it, so put no secret in a key.

A send or a call needs the sender's permissions, a send or call job's own
`allow:` and `deny:` included, to hold `send:<location>`, and the receiver's
`receive:` to accept the sender.

  receive: [thermostats/*, client:panel]                                 for every event
  receive: { set: [thermostats/*, client:panel], stop: [client:panel] }   by event name

- With no `receive:`, a file accepts its own tree and its tree's client. A
  written `receive:` replaces the tree with its list, and the tree's client is
  accepted whatever the list says.
- A call is checked against a list. A mapping takes a call only from the
  tree's client.
- The run reads the sender as `event.from`: `{ at, run }`, with `key` for a
  keyed run, or `{ client }`. A run reads its own address as
  `${run.address}`, and its key as `${run.key}`, which is null except at a keyed
  location.
- The run reads the principal a client sent an event for as
  `event.principal`, and the principal a client started it for as
  `run.principal`. A gateway names the principal of its caller's token
  (`corbie manual gateway-clients`). Each is empty when the client named none.
- A send to a transient location starts a new run with the event's data as
  its input. A statechart is then given the event; any other machine is given
  only the start.
- A send the receiver refuses, or that no running statechart can take, is
  noted as undelivered in the sender's record and fails nothing, after the
  sender's end if it has ended.
- What a machine made while running may address is under Words from outside.

A file's `read:` lists clients, beside its tree's, that read its runs: their
records, tickets and files, and those of the runs below them.

  read: [client:wall]          wall lists and shows the runs, and reads their records
  receive: [client:wall]       wall sends to them too

- A listed client does not own the tree. It cannot submit there or cancel the
  runs.
- A run keeps the list it started with.
- A client the controller does not trust reads nothing. The submit prints its name.

Events
------

The controller sends events to a machine. An event has a name, a source and data.

  start     the run's input
  done      a job ended well; data is its output
  failed    a job failed; data is { status, error, output }
  <name>    a timer that is due, a ticket's answer, an event from the parent run,
            a child run, the client (`corbie run send`) or a send to the run's
            address, or a value a job emitted with emit(name, value)

No client, machine or script can send an event named `start`, `done`, `failed`
or `timer`. A send under one of the receiver's timer or ticket names is noted
as undelivered.

A failed job's status is `error`, `timeout`, `denied` or `cancelled`, and
`denied` adds `refused`, `layer` and `fix` to the data. Each type's page lists
the events it acts on.

Hooks
-----

`corbie manual hooks` has the mechanism and an example. A hook is a job that
runs before or after the jobs of its machine and of the machines it runs.

  hooks: { small: { before: ./small.js, when: "${job.approve}" } }    a hook named `small`

  before: ./small.js                 a job that runs before a job starts
  after: { machine: ./mask.yaml }    a job that runs after a job has ended `done`
  when: "${job.approve}"             a condition on the job; with none, every job

A hook writes one of `before:` and `after:`. Its job is a script, a machine, a
call or a send.

  { ok: true }           before a job: it goes on. After a job: the machine is given its output
  { ok: true, input }    before a job: it starts with that input
  { ok: true, output }   after a job: the machine is given that output
  { ok: false, note }    before a job: it fails with status `denied`. After a job: it fails
  any other result       as `{ ok: false }`

- A hook that fails, or whose `when:` or values cannot be filled in, refuses the job.
- A hook that is a send returns nothing, and refuses nothing.
- A refused job's error holds the hook's name and its note.
- A changed input changes no permission: the job's `allow:` is filled first.
- The run's record holds each hook's result. The machine is not told of a
  changed input: a stage's own values and an agent's conversation hold what
  was first asked for.
- After a hook gives another output, the record still holds the job's own.

A hook's expressions read `input`, `values` and `run` of the machine that names
it, and `job`. After a job they read `output`, the job's output.

  job.name       the stage, state or tool that asked for the job
  job.run        the run the job is a job of: { id, machine }
  job.input      the input the job is given
  job.allow      the permissions the job declares
  job.approve    true when the job is marked for approval
  job.meta       the job's `meta:`
  job.script, job.machine, job.call or job.send    what the job runs
  job.tool       for an agent's tool call: { name, entry, toolkit, description, args, said }

- A hook with no `input:` is given `{ job }`, and after a job `{ job, output }`.
- A hook's `allow:` scopes read `input` and `values`, and never `job`.
- A hook's job has its own `allow:` and `deny:`, and those of the definition that writes it.
- A hook is not named `cancel`, and its `machine:` is a file, not an expression.
- A hook's job is named for the job and the hook, as `refund.0.small`.

Which hooks run for a job:

- Every hook whose `when:` holds runs, one at a time: the machine's own in the
  order of their names, then those of each machine above it, the nearest first.
- A hook runs once for one job. A hook's own job takes no hook.
- A machine run as a hook takes no hook and no `approve:` list from above it.
- A run started by a send or a call takes only its own file's hooks.
- A job that is no longer wanted while a hook runs for it is dropped, and the
  hook's job is cancelled.
- A hook has no time limit of its own: its job's `timeout:` is how long it may take.

A job is marked for approval in two cases.

- The job has `approve: true`.
- The job's `allow:` list declares a permission that `approve:` lists, in
  kind and their scopes match a common value, or when one is a group of that kind.
  A call or a send job declares only `send:` for its location.

A marked job starts only after a `before` hook, with no permission it did not
have. One that no `before` hook is for fails with status `denied`, and a run of
a definition that marks a job and has no `before` hook in it or above it is
refused as it starts.

A script hook runs alone under `corbie test`. This one refuses a job whose
`allow:` list has an `fs.write` entry.

    // writes.js
    const writes = (input.job.allow || []).some(a => a.startsWith("fs.write"))
    return { ok: !writes, note: "writes are not approved here" }

    corbie test writes.js --input '{"job": {"name": "tidy", "allow": ["fs.write:/srv/**"]}}'
      output: {"note":"writes are not approved here","ok":false}

Words from outside
------------------

A machine made while running, which a script or a model wrote, and the tools a
`list:` gives an agent are words from outside. They name no hook and no address.

- A machine made while running writes no hooks: one that does fails as it
  starts. The hooks above it that were not made while running run for its
  jobs, and its jobs give them no `meta`.
- A machine made while running sends only to its parent and its children. A
  send to an address or a call fails it.
- A machine made while running writes the names of its jobs and tools. Write a
  hook for its jobs with `when: "${job.approve}"`, and not with a name.
- A tool from a `list:` runs the entry's `job:`, which the definition writes,
  and takes the agent's hooks as any tool does.
